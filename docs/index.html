This is the teammate copy.

It holds the registration token and the shared application secrets, and none of the owner's identity — no passphrase, no keystore, no account password. The values are real all the same: keep the file private (chmod 600), never in git or a group chat. Start at Bring a teammate in; blurred values show when you click them.

Bring a teammate in

A teammate gets an identity and an account of their own, joins the univers42 organisation, and is granted the prod environment of project groot. From then on one make command gives their machine the same secrets and the same seven databases as this one. Nothing of the owner's changes hands except the registration token.

Where data lives, and who can open it

vault42 seals every file on the machine that sends it, and who can open the file later depends only on what it was sealed to. Three spaces, three answers:

Personal spaces never collide: a teammate's 42ctl push --project groot lands in their own namespace, because every stored name is derived from the pusher's principal (42ctl src/ops/sync.rs:486) and the server filters every read by owner (vault42-server secret_read.rs:13). The other side of that coin: a teammate cannot read the owner's personal groot, which is the trap below.

The trap — a teammate's plain make all lands in LOCAL mode

make all pulls the personal project. Under a teammate's identity that project is empty — measured: no manifest for project groot (push first, or pass --project) — so the machine falls back to self-generated secrets, loads the old git snapshot, drops .vault42-local-mode, and skips the vault on every later run. Undoing that means wiping the data volumes. A teammate pulls the team environment first: make vault42-team-pull APPLY=1, or make all VAULT42_SOURCE=team, which stops with an error instead of falling back.

*.local never reaches a teammate

The team push seals every *.local file to the pusher alone: a teammate sees neither its bytes nor its name (measured: 0 of 6). apps/grobase/.env.local holds the owner's Fly, Vercel, npm, Docker, GitHub and Sonar tokens and stays with the owner. The root .env.local is rebuilt on the teammate's machine from the shared apps/grobase/.env, then the few lines that point into the seeded data are laid over it from the shared secret team/env-local (step b). The mail, calendar, website and osionos .env.local files are optional per-developer OAuth clients; Compose loads them with required: false.

Once, before the first teammate

owner

Three uploads the live run found missing. They send data to the vault, so the owner runs them by hand (agents are blocked from sending secrets off the machine), signed in for the session.

  1. Seal the object-store pair into the environment

    owner

    Files over 4 MiB — the MinIO and WordPress archives — travel as chunks in the Tigris bucket, and pulling them needs FT_S3_KEY and FT_S3_SECRET. Today the pair sits only in the owner's personal vault. Sealed to the environment, every member can read it and make vault42-team-pull loads it by itself.

    terminal
    for p in infra/S3_KEY infra/S3_SECRET; do \
  v=$(42ctl vault get "$p") || { echo "!! $p: not in your personal vault"; continue; }; \
  [ -n "$v" ] || { echo "!! $p: empty — refusing to publish"; continue; }; \
  printf '%s' "$v" | 42ctl env secret set --org univers42 --project groot --env prod "$p"; \
done
✓ set infra/S3_KEY (v1)
✓ set infra/S3_SECRET (v1)
for p in infra/S3_KEY infra/S3_SECRET; do \
  printf '%-18s %s bytes\n' "$p" "$(42ctl env secret get --org univers42 --project groot --env prod "$p" | wc -c)"; \
done
infra/S3_KEY       20 bytes
infra/S3_SECRET    40 bytes

    Two ✓ set lines, then two byte counts well above zero. This pair can delete chunks as well as read them; a read-only Tigris key for read-only teammates would be tighter, and none exists yet.

    Why the loop, and not a plain pipe.

    Write it as 42ctl vault get infra/S3_KEY | 42ctl env secret set … infra/S3_KEY and a failure on the left — a typo in the path, a case slip such as infra/S3_key, a vault that simply does not hold it — produces nothing on stdout while the right-hand side still stores it and prints ✓ set … (v2). You now have an empty secret that reports success, and every teammate fails later with FT_S3_KEY and FT_S3_SECRET are not set — an error that names the symptom and not the cause. Measured on this project: exactly that typo published an empty infra/S3_KEY, and the next run bumped it to v3 only because the path was retyped correctly by luck. The guard above refuses to write an empty value, and the byte counts prove what landed.

  2. Share the team half of the root .env.local

    owner

    .env.local is private, so a teammate's copy is rebuilt by scripts/gen-local-env.sh from the shared backend keys. That script mints fresh osionos secrets and knows nothing of the live mounts. Two kinds of line must match the seeded data: OSIONOS_BRIDGE_EMAIL_HASH_SALT salts the email_hash column of osionos_bridge_identities (bridge-api.mjs:254), so with a fresh salt the restored identities are never found again; the VITE_BAAS_* lines name tenants, mounts and tables inside the restored database. Publish those lines, and only those:

    terminal
    grep -E '^(OSIONOS_BRIDGE_EMAIL_HASH_SALT|OSIONOS_BAAS_API_KEY|VITE_BAAS_[A-Z_]+)=' .env.local \
| 42ctl env secret set --org univers42 --project groot --env prod team/env-local
42ctl env secret get --org univers42 --project groot --env prod team/env-local | cut -d= -f1
OSIONOS_BRIDGE_EMAIL_HASH_SALT
OSIONOS_BAAS_API_KEY
VITE_BAAS_API_KEY … (every VITE_BAAS_ line, 15 in all)

    The key names only, no values. Never share the rest of the file: DOCKER_*, FLY_API_TOKEN, SONAR_TOK, GITHUB_PAT, GIPHY_API and EMAIL_RECUP_ADMIN_VAULT are the owner's; OSIONOS_RUNNER_URL, OSIONOS_IDE_* and VITE_OSIO_IDE are per machine; PERMS_SERVICE_* stays blank.

For each teammate

Two machines, alternating. Each hand-off is one short private message: the registration token, the sign-up email, the invite token, “done”.

  1. Install Docker, git and 42ctl

    teammate

    Ubuntu on x86_64 or aarch64 — the only published 42ctl builds. The usermod line lets you use Docker without sudo; the installer checks the download's SHA-256 against the release before putting it in ~/.local/bin.

    terminal
    sudo apt update && sudo apt install -y docker.io docker-compose-v2 git make curl openssl
sudo usermod -aG docker "$USER" && newgrp docker
curl -fsSL https://raw.githubusercontent.com/Univers42/42ctl/main/install.sh | sh
export PATH="$HOME/.local/bin:$PATH"
42ctl version
42ctl 0.1.12
42ctl config show
server    https://vault42-server.fly.dev
authority https://vault42-authority.fly.dev

    42ctl 0.1.12 or newer, and exactly those two addresses. vault42.fly.dev is somebody else's app.

    20 GB free under /var: a fresh make all measured 14.1 GB of images and build cache, plus about 1 GB of restored data. Check with df -h /var.

  2. Create your identity

    teammate

    One keypair, generated on your machine and locked with a passphrase you choose. It is what every file will be sealed to for you. It is not the owner's identity: never copy their keystore.v42, never type their passphrase.

    terminal
    42ctl keys init
passphrase: choose one, and put it in a password manager now
identity created
principal 60cab039…
address   v42:…
42ctl keys export-pub
v42:…       ← your public address, safe to share

    identity created, and ~/.config/42ctl/keystore.v42 with mode 600. Nobody can reset the passphrase: lose it and everything sealed to you is gone.

  3. Create your account and take a contract

    teammate

    The account — email and password — is who you are to the control plane: organisations, grants, invites. Sign-up is closed; it needs the registration token below, which the owner passes on. The account password is a different secret from your passphrase.

    terminal
    export FT_REGISTER_TOKEN=''
42ctl auth signup --email you@example.com
password: choose one, 12 characters or more
if you@example.com was not already registered, it is now — log in to obtain a session
42ctl auth login --password --email you@example.com --tenant yourname
logged in to 'yourname' on profile 'default'
42ctl auth whoami
contract  bound (profile 'default')
unset FT_REGISTER_TOKEN

    logged in to 'yourname' and contract bound. The tenant is your permanent handle: 1 to 64 characters from A–Z a–z 0–9 _ -, first come first served (409 tenant name is taken), the same on every machine. Sign-up answers the same sentence whether or not the email already had an account; the login is the real test. Then tell the owner the exact email you used — the invite is bound to it. Optional: 42ctl auth mfa --on emails a code at every sign-in.

  4. Invite them into the organisation

    owner

    Needs the owner session (the sign-in pane above). The token is good for 7 days and one use, and only an account signed in with that exact email can redeem it. There is no revoke command, so send it privately and promptly — a password-manager share or an end-to-end encrypted chat, never git, an issue or a group channel.

    Wait for their step 3 first. The invite binds to the email they actually signed up with. Invite a typo of it and the token is dead — no revoke, and you issue a second one. Ask them to paste the exact address back to you before you run this.

    terminal
    42ctl org member ls --org univers42          # before: note who is already in
7704efb0-…  owner  3d ago
42ctl org invite --org univers42 --email them@example.com --role member
invite_id 4db61503-…
token     43 characters, shown once
invited them@example.com to org 'univers42' as 'member'

    invited … as 'member'. member is the right org role; owner and admin can invite and remove people.

    The token prints once.

    Copy it out of the terminal before you run anything else — there is no command that shows it again, and scrollback in a cleared or closed pane is gone. If you lose it, re-run the invite: a second token for the same email is harmless.

    Being an org member is not access to anything. It only lets them be granted. After they accept you will see their id in org member ls, and they will still read nothing — that is expected until step 6. An id that shows up in org member ls but never in env keys ls has no project grant.

  5. Accept the invite and publish your public keys

    teammate

    keys enroll is the step people skip, and skipping it is silent. Accepting the invite makes you an org member; enrolling publishes the public half of your identity so the owner's env keys sync has something to wrap the environment key to. Without it that sync reports skipped 1 (no registered pubkey) and you stay unable to read anything — with no error on your side.

    terminal
    42ctl invite accept --token 'the-invite-token'
accepted invite
42ctl keys enroll --org univers42
pubkey enrolled in org univers42 — an admin can now provision environment keys to you
42ctl keys export-pub                        # your address; send it if asked
v42:…

    accepted invite, then pubkey enrolled. A 403: you are signed in with a different email than the one invited. A 409: the invite expired or was already used — ask for a new one. Then tell the owner you are done: they cannot proceed until your public key is up.

    Do not run env init.

    Until the owner finishes step 6, every env command answers no scope key for this env — run env init first. That message is wrong for you. env init bootstraps a new key for the whole environment and would orphan everyone else's wraps. You are not missing an environment; you are missing your wrap of it, and only the owner can create that. On an environment that already has a key the command refuses anyway — already has a scope key (epoch 1) with N provisioned member(s) — which is the safe outcome, not a problem to solve.

  6. Grant prod and wrap its key to them

    owner

    read is the right default: the server refuses env writes from a read-only member, and a writer's push replaces what everyone pulls next. The key is wrapped only to an account that is all three — org member, granted, enrolled — which is what env keys sync checks. Run this after they confirm step 5; a sync before they enrol silently provisions nobody.

    terminal
    42ctl project grant add --org univers42 --project groot --user them@example.com --role read --env prod
grant_id  2dc6d608-…
granted them@example.com 'read' on project 'groot'
42ctl project grant ls --org univers42 --project groot
…  user  …  read  5f8221ab-…      ← the prod env id, NOT (project-wide)

…  true    false        pending-provision

provisioned 1
skipped   0 (no registered pubkey)
42ctl env keys ls   --org univers42 --project groot --env prod
…  true    true         active

    provisioned 1 with skipped 0, then their row reads active. For several people at once: team create, team member add, then team grant --role read --env prod.

    Read the two numbers, not just the tick. skipped N (no registered pubkey) means those people never ran keys enroll — send them back to step 5 and re-run the sync; it is safe to repeat. provisioned 0 with skipped 0 means nobody is waiting: either they are already active, or they hold no grant on this environment and never appear in this list at all.

    If you forgot --env prod.

    Omitting it grants the project as a whole, and project grant ls then shows (project-wide) in the Env column. That still works, but it is wider than intended and outlives any single environment. Narrow it with the grant id from the listing:

    terminal
    42ctl project grant rm  --org univers42 --project groot --grant <grant_id>
42ctl project grant add --org univers42 --project groot --user them@example.com --role read --env prod
42ctl env keys sync     --org univers42 --project groot --env prod

    An id in org member ls that never appears in env keys ls has no grant on this environment. That is the single most common reason a teammate reports no manifest for project groot while everything looks fine from the owner's side — being an org admin grants nothing here.

    teammate

    With the tree in place, make all finds apps/grobase/.env and skips the vault, makes and trusts a local HTTPS certificate (one sudo prompt), starts the backend, loads all seven databases from ./secrets because the engines are empty, then builds and starts the apps.     Already in LOCAL mode?

    If make all printed THIS MACHINE IS IN LOCAL MODE, the volumes were initialised with self-generated secrets. Recovery deletes this stack's local data volumes on this machine and nothing else: docker compose -p mini-baas down -v --remove-orphans, then rm -f apps/grobase/.env apps/grobase/.env.secrets apps/grobase/.env.local ./.env.local .vault42-local-mode, then make vault42-team-pull APPLY=1 && make all.

Their own seeds, private to them

teammate

Everything in the team environment is shared with everyone granted prod. Data that is yours alone — a database you have been filling, an experiment on the seeds — goes in your personal space, sealed to your identity, invisible to everyone including the owner. The owner's make targets work for you unchanged; they just open your groot. Give your vault the object-store pair once, then capture and push.

terminal
printf '%s' "$(42ctl env secret get --org univers42 --project groot --env prod infra/S3_KEY)"    | 42ctl vault set infra/S3_KEY
printf '%s' "$(42ctl env secret get --org univers42 --project groot --env prod infra/S3_SECRET)" | 42ctl vault set infra/S3_SECRET
make vault42-seed              # dumps every running engine into ./secrets
make vault42-push-all          # seals the whole tree to YOU, *.local included
make vault42-pull-all          # dry run: everything "in sync"

On a second machine of yours: 42ctl keys escrow here, 42ctl keys recover there, then 42ctl auth login --password --email … --tenant … (recover restores the key, not the contract), then make vault42-pull-all APPLY=1 and make vault-restore. Never keys init on the second machine. ./secrets holds one seed set at a time: sh scripts/vault42-team.sh pull --apply --only 'secrets/*' brings the team's back, make vault42-pull-all APPLY=1 FORCE=1 brings yours, make vault-restore loads whichever is on disk.

Org roles are separate: owner and admin invite and remove people, never above their own rank; member is what a teammate gets. Changing somebody's project role needs env keys rotate: env keys sync only wraps members who hold no key yet, while a rotation re-wraps everyone at their current role.

Day to day

  • HTTP 401 from an org, project or env command: the 24 h session ran out — 42ctl auth login --password --email … --tenant ….
  • New team data: make vault42-team-pull, read the preview, then APPLY=1. The selected files are overwritten.
  • Writers publishing: make vault42-team-push from a complete checkout; your *.local files stay yours.
  • After a rotation you do nothing: the owner's rotate re-wraps you at your current role.
  • 42ctl vault audit lists what was written and when; 42ctl update --check keeps you on a signed build.

When someone leaves

owner
terminal
42ctl org member rm --org univers42 --user them@example.com       # teams, groups, grants, pubkey go too
42ctl env keys rotate --org univers42 --project groot --env prod   # fresh key, re-sealed, re-wrapped to who is left

Removal ends authorisation; rotation ends access to anything sealed afterwards. What they already pulled, they keep: every value in apps/grobase/.env sat on their disk in clear. When a departure calls for it, also rotate the backend secrets (Making new secrets), the Tigris pair, and the registration token if they still know it.

42ctl and make, at a glance

42ctl help kickoff is the built-in walkthrough; 42ctl <command> --help gives exact flags. Run make commands from ~/Documents/Groot.

CommandWhat it does

Environment variables 42ctl reads

VariableMeaning
FT_PASSPHRASEUnlocks the keystore without a prompt. Required when no terminal is attached (scripts, make), or it fails with os error 6.
FT_CONFIG · FT_KEYSTOREPaths to config.json and keystore.v42. Default: ~/.config/42ctl/.
FT_S3_KEY · FT_S3_SECRETObject-store pair for files over 4 MiB.
FT_PASSWORD · FT_LOGIN_EMAILAccount password and default email for auth login --password without prompts. A different secret from the passphrase.
FT_REGISTER_TOKENThe registration token, read by auth signup so it never sits on the command line.
VAULT42_TEAM · VAULT42_SOURCEmake: the team environment (org/project/env, default univers42/groot/prod) and which source make all pulls from (personal, the default, or team).
FLY_API_TOKENFor 42ctl cloud.
RUST_LOG=debugVerbose output when a transfer misbehaves.

Files the tools leave behind

  • ~/Documents/Groot/.vault42-local-mode — this machine fell back to self-made secrets because the vault could not be reached.
  • ~/.local/state/groot/restore-in-progress — a vault restore started and did not finish; make all refuses to continue until you resolve it.
  • ~/.local/state/grobase/vault-restore/ — Postgres backups taken just before each restore.
  • ~/.local/state/grobase/migrations/ — dumps taken before database migrations.

When something fails

You seeWhyDo this
os error 642ctl wanted to ask for the passphrase but has no terminal.export VAULT42_PASSPHRASE='…' (or FT_PASSPHRASE) before the command.
“stored as N chunk(s) … FT_S3_KEY”A bare 42ctl pull without the object-store pair.Use make vault42-pull-all, which fetches the pair first.
“THIS MACHINE IS IN LOCAL MODE”make all ran before the identity files (step 3) were in place, or the vault pull failed. The backend then made its own secrets and loaded the old git snapshot; from then on every make all skips the vault.Prove the vault works, changing nothing: export VAULT42_PASSPHRASE='…' then make vault42-pull-all (54 file lines, then “pull completed”). Then reset this machine’s local data and pull for real: docker compose -p mini-baas down -v --remove-orphans, rm -f apps/grobase/.env apps/grobase/.env.secrets apps/grobase/.env.local ./.env.local .vault42-local-mode, make vault42-pull-all APPLY=1 FORCE=1, make all. A teammate: the same reset, then make vault42-team-pull APPLY=1 and make all.
no manifest for project grootA personal pull under an identity that never pushed — a teammate running make vault42-pull-all or plain make all.make vault42-team-pull APPLY=1. If make all already ran, the LOCAL MODE row above.
HTTP 401 from org, project or env commandsThe session is older than 24 h.42ctl auth login --password --email … --tenant …
Sign-up refused with 401Missing or outdated registration token.Ask the owner for the current one.
Sign-up “accepted”, login 401The email already had an account, or a typo — sign-up never says which.Use the original password, or the right email.
409 tenant name is takenSomeone holds that handle.Pick another.
Invite accept: 403 / 409Signed in as a different email than invited / the invite expired (7 days) or was used.Log in as the invited email, or get a new invite.
“no scope key for this env — run env init first”No key wrapped to you yet.Owner: grant + env keys sync. Never run env init — it makes a new key for the whole environment.
pending-enrollment / pending-provision in env keys lsNo public key published / enrolled but not wrapped yet.Teammate: 42ctl keys enroll --org univers42 / owner: env keys sync.
“a read-only member of this scope may not write its env secrets”You hold read; the server refused (measured).Owner: grant write, then env keys rotate.
contract none in auth whoamiLogged in without --tenant, or just recovered a keystore.42ctl auth login --password --email … --tenant …
“no file in environment 'prod' matches …”An --only pattern typo.Patterns match the stored relative path; * crosses /.
“FT_S3_KEY and FT_S3_SECRET are not set” on a team pullA chunked seed, and step a has not put the pair in the environment.Owner: step a. Meanwhile: export FT_S3_KEY=… FT_S3_SECRET=… before the pull.
“a vault restore started … never finished”A restore was interrupted; some databases may be empty.make vault-restore, then rm ~/.local/state/groot/restore-in-progress.
“vault seeds failed verification”A dump does not match SHA256SUMS.make vault42-pull-all APPLY=1 FORCE=1; if it persists, re-run make vault42-seed and push on the source machine.
401 on every request after a restoreSecrets and database volumes come from different generations.make -C apps/grobase reconcile-credentials, then make frontends-up.
Browser: certificate warningThe local authority is not trusted on this machine yet.make certs-trust-local, then restart the browser.
Settings → Permissions: “not available”The permission engine refused the bridge's credentials.Keep PERMS_SERVICE_* blank in .env.local; docker compose --env-file ./.env.local up -d --build osionos-bridge.
Share dialog: “not available”The share-rules table is missing (older snapshot).docker exec -i mini-baas-postgres psql -U postgres -v ON_ERROR_STOP=1 < models/osionos-share-rules-migration.sql
IDE terminal: “enable the workspace sandbox”The sandbox is off or its network rules are missing.The optional sandbox setup above.
MSSQL and DynamoDB not running after make allThey belong to the optional “extra engines” group, off by default to save memory.The optional SQL Server and DynamoDB step above, then make vault-restore.
Ports 3002 / 3003 answer 502Mail and calendar are not started by make all.Nothing; expected.
Mongo shows “unhealthy” for a whileIts health check takes up to 10 s on a busy machine.Wait a minute, run docker ps again.
A build ends with “Killed”Out of memory (6 GB machines).docker stop mini-baas-mssql mini-baas-dynamodb-local, rebuild, then docker start them.
“no space left on device”Build cache and old images filled /var.docker builder prune -f --filter type=regular (keeps the dependency caches that make rebuilds fast), then docker image prune -f. Never docker system prune --volumes: the volumes hold your data.
Passphrase lost

Nobody can decrypt the vault, by design. Make a new identity (Making new secrets) and push again from a machine that still has the files.

Keystore lost, passphrase known

Step 3 rebuilds it from the text on this page; or 42ctl keys recover if you escrowed it; or decode it from the GitHub secret.

vault42 unreachable

make all falls back to local mode and never touches existing data. Check 42ctl cloud health, wait, pull again.

Restored in the wrong direction

The Postgres state from just before is in ~/.local/state/grobase/vault-restore/. The other engines: re-seed from the machine that has the right data.
